# OpenCode — Agent Workflow Instructions

> **Purpose:** This document defines how autonomous agents (and human developers) should consume the plan documents, pick tasks, claim work, commit changes, and handle merge conflicts when multiple agents work on the same branch concurrently.

> **Note for agents:** Read this document **before** starting any task. Follow these instructions exactly. If any step is unclear, ask for clarification.

---

## 0.1.1 Overview

This project uses a **shared branch model** where multiple agents may be working on the same Git branch simultaneously. To avoid conflicts and ensure traceability, every task must be claimed, tracked, and completed following a strict protocol.

**Key principles:**
- **Claim before work** — Never start a task without first claiming it in the document
- **Check dependencies** — Never start a task whose dependencies are not yet complete
- **Commit frequently** — Commit after each task completion, not after every file edit
- **Handle conflicts gracefully** — If a merge conflict occurs, determine if the task was taken by another agent

---

## 0.1.2 Task Selection

### 0.1.2.1 How to Pick a Task

1. **Consult the TOC** — Open [`0.0-OpenCode-TOC.md`](./0.0-OpenCode-TOC.md) to understand the document structure
2. **Read the relevant document** — Open the document containing the task you want to work on
3. **Find an unclaimed task** — Look in the task tables for a row where:
   - `Status` is empty or `⬜ PENDING`
   - `Assigned To` is empty
4. **Check dependencies** — Verify that all tasks listed in the `Dependencies` column are marked as `✅ DONE`
5. **If dependencies are not met** — Do NOT start the task. Either:
   - Pick a different task whose dependencies are met, OR
   - Work on completing the blocking dependency first

### 0.1.2.2 Priority Order

Tasks should generally be worked on in the following order:

1. **Phase F0 tasks** (project setup) — highest priority, foundational
2. **Phase F1 tasks** (core implementation) — enables FreeBSD support
3. **Phase F2 tasks** (testing/CI) — quality assurance
4. **Phase C tasks** (code quality) — ongoing improvements

## 0.1.3 Claiming a Task

### 0.1.3.1 Before You Start

Before claiming a task, ensure:

- [ ] You have read this workflow document
- [ ] You have read the relevant plan document(s)
- [ ] You understand the task requirements
- [ ] All dependencies are marked as complete
- [ ] No other agent has claimed the task (check `Assigned To` column)

### 0.1.3.2 How to Claim

To claim a task, update the task table row in the document:

1. **Set `Status`** to `🔄 IN PROGRESS`
2. **Set `Assigned To`** to your agent identifier using the hostname (e.g., `freedev002`). Use the `hostname` command to identify your system.
3. **Leave `End` empty** — will be filled on completion

**Example — Before claiming:**

| ID | Area | Task | Status | Assigned To | Dependencies | Files | Notes |
|----|------|------|--------|-------------|--------------|-------|-------|
| F1.3 | PTY | Verify node-pty FreeBSD support | ⬜ PENDING | | F1.1 | `src/pty/pty.node.ts` | |

**Example — After claiming:**

| ID | Area | Task | Status | Assigned To | Dependencies | Files | Notes |
|----|------|------|--------|-------------|--------------|-------|-------|
| F1.3 | PTY | Verify node-pty FreeBSD support | 🔄 IN PROGRESS | freedev002 | F1.1 | `src/pty/pty.node.ts` | |

### 0.1.3.3 Commit After Claiming

After claiming a task, immediately commit and push the change:

```bash
git add .plan/0.0-OpenCode-TOC.md
git commit -m "Claim task F1.3: Verify node-pty FreeBSD support"
git push
```

**Important:** You must push immediately after committing. Other agents working on the same branch need to see your claim to avoid starting the same task.

## 0.1.4 Working on a Task

### 0.1.4.1 Implementation Guidelines

1. **Follow the plan** — Implement exactly what the task describes. Do not add scope.
2. **Follow code style** — Match the existing codebase conventions (see `AGENTS.md`):
   - Use cross-platform Node.js APIs (e.g., `fs.promises` over `Bun.file()`)
   - Avoid `try`/`catch` where possible
   - Avoid unnecessary destructuring
   - Prefer early returns over `else` statements
   - Use functional array methods (flatMap, filter, map)
3. **Write tests** — Every task that involves code changes should include tests
4. **Update cross-references** — If you change a section number or file name, update all cross-references
5. **Document as you go** — Update KDoc/comments in code, not just plan documents

### 0.1.4.2 Platform-Specific Code

When adding platform-specific code:

1. Use conditional imports with `bun`, `node`, and `freebsd` conditions
2. Follow the pattern established in `packages/opencode/package.json`:
```json
"#pty": {
  "bun": "./src/pty/pty.bun.ts",
  "node": "./src/pty/pty.node.ts",
  "freebsd": "./src/pty/pty.node.ts",
  "default": "./src/pty/pty.bun.ts"
}
```
3. Prefer Node.js implementations for FreeBSD when possible

### 0.1.4.3 If You Get Stuck

If you encounter an issue that blocks progress:

1. **Try 3 genuine fix attempts** — Document what you tried and why it didn't work
2. **Mark the task as blocked** — Set `Status` to `🟡 BLOCKED` and add the reason to `Notes`
3. **Commit and push** — So other agents know the task is blocked
4. **Ask for guidance** — Use the `ask_user_v2` tool to explain the issue

### 0.1.4.4 If the Task is Impossible

If a task cannot be completed as described (e.g., design flaw, missing dependency, technical limitation):

1. **Mark the task as `❌ FAILED`** — Set `Status` to `❌ FAILED`
2. **Document why** — Add the reason to `Notes`
3. **Commit and push**
4. **Move to the next task** — Do not block on failed tasks unless they are critical dependencies

## 0.1.5 Completing a Task

### 0.1.5.1 How to Mark Complete

When a task is fully implemented and verified:

1. **Run all relevant tests** — Execute the full test suite for the affected module(s). Do NOT consider a task complete unless **all** unit tests pass.
2. **Run typecheck** — Execute `bun typecheck` from the package directory
3. **Set `Status`** to `✅ DONE`
4. **Set `End`** to the current date/time in ISO 8601 format: `YYYY-MM-DD HH:MM UTC`
5. **Update `Notes`** — Add a brief summary of what was implemented (1-2 sentences)
6. **Update `Files`** — Ensure all files created/modified are listed

**Example — After completion:**

| ID | Area | Task | Status | Assigned To | Dependencies | Files | Notes |
|----|------|------|--------|-------------|--------------|-------|-------|
| F1.3 | PTY | Verify node-pty FreeBSD support | ✅ DONE | freedev002 | F1.1 | `src/pty/pty.node.ts` | node-pty 0.8+ supports FreeBSD |

### 0.1.5.2 Commit After Completion

After marking a task complete, commit and push:

```bash
git add -A
git commit -m "Complete task F1.3: node-pty FreeBSD support verified"
git push
```

### 0.1.5.3 Update TOC

After completing a task, update the TOC document to reflect the new status:

```bash
git add .plan/0.0-OpenCode-TOC.md
git commit -m "Update TOC: F1.3 marked complete"
git push
```

## 0.1.6 Handling Merge Conflicts

### 0.1.6.1 If You Encounter a Conflict

1. **Pull the latest changes** — `git pull --rebase`
2. **Check if another agent claimed the same task** — Look at the task table in the relevant document
3. **If the task was taken by another agent:**
   - Abandon your work on that task
   - Pick a different unclaimed task
   - Commit your partial work as a WIP if valuable
4. **If it's just a text conflict in plan documents:**
   - Merge the changes carefully
   - Ensure all agent claims are preserved
   - Push the resolved conflict

### 0.1.6.2 Conflict Resolution Guidelines

When merging conflicting task claims:
- Preserve the **earlier claim** (first to push wins)
- Add a note in `Notes` about the conflict resolution
- Do NOT overwrite another agent's claim without explicit approval

## 0.1.7 Testing Requirements

### 0.1.7.1 Running Tests

Tests cannot run from repo root. Run from package directories:

```bash
cd packages/opencode
bun test
```

### 0.1.7.2 Type Checking

Always run typecheck before completing a task:

```bash
cd packages/opencode
bun typecheck
```

On FreeBSD (where Bun may not be available):

```bash
cd packages/opencode
npx tsgo --noEmit
```

---

## 0.1.8 Build Requirements

### 0.1.8.1 Building OpenCode

To build OpenCode with FreeBSD support:

```bash
cd packages/opencode
bun run build
```

This will build all platform targets including FreeBSD.

## 0.1.9 Code Style Checklist

Before committing, verify your code follows the style guide:

- [ ] Uses cross-platform Node.js APIs (fs.promises, not Bun.file())
- [ ] No unnecessary try/catch blocks
- [ ] No unnecessary destructuring
- [ ] Uses early returns, not else statements
- [ ] Uses functional array methods (map, filter, flatMap)
- [ ] No `any` types
- [ ] Uses const over let
- [ ] Comments added for complex logic
- [ ] Platform-specific code uses conditional imports
